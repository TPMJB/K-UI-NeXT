# K-UI 2.0 candidates and hardware gates

Planning notes, 2026-10-06. These are candidates, not implemented features or
hardware validation. Aim for a useful final release that other contributors
can maintain without another broad feature expansion.

K-UI is a shell, launcher and application runtime built on KallistiOS. KOS
provides the underlying kernel and hardware services; its own documentation
describes it as a development library and unikernel operating system.

## Proposed core

1. **Hardware-tested IDE/CF support.** Establish correct device detection,
   reset, data integrity and retained GD-ROM operation first. Then implement
   negotiated ATA DMA with correct completion, timeout and cancellation
   behavior. Measure actual games and ripping separately. Retain the working
   SCI and SCIF paths. G1 bus ownership must be explicit when both GD-ROM and
   CF are involved; do not assume two transfers on that bus can overlap.
   Effort: high, gated on hardware.
2. **One game entry with saved launch settings.** Group an original GDI and
   its 2048 copy, allow an explicit variant choice, and remember each title's
   successful reader/video settings. Include a way to restore the recommended
   settings and show which variant/settings are about to launch. The current
   batch converter already creates separately selectable sibling folders;
   an experimental selector build now groups matching sibling copies. Saved
   per-title settings remain future work. Effort: medium.
3. **Complete console updates with rollback.** Install the matching runtime
   and apps as one verified package, stage it before activation, and retain a
   previous working package. Extend the existing updater and runtime fallback
   rather than presenting either as a new feature. Effort: medium/high.

## Useful additions if they fit

- **Shareable compatibility profiles:** export the game identity, K-UI build,
  storage path, variant, settings and observed result. Import proven settings
  without treating an untested report as a compatibility guarantee.
- **Automatic VMU snapshots:** extend the existing verified manual backup
  path to copy changed saves before launching, with bounded retention and a
  simple restore view.
- **Contributor starter kit:** document app/storage interfaces, saved-profile
  format and reproducible builds; provide one small example app. A general
  returning-executable plugin loader would be a separate, larger project.

## IDE/CF verification before layout acceptance

The recovered `dreamshell_next_g1_cf_revA_design_pack.zip` is six text/CSV
files: mappings, power table, BOM, sources and planned CF reference. It contains
no finished schematic, PCB, Gerbers or hardware acceptance evidence. Its VA1
target does not identify the user's Samsung 3.3 V GD-ROM variant. Rev A describes
a 5 V commodity adapter; Rev B proposes direct 3.3 V CF. Those assumptions must
be resolved for the exact installation, not copied into a final PCB unchanged.

- Verify the actual board/drive markings, connector orientation, every proposed
  net and mechanical fit, using traceable references and physical measurements.
- Resolve drive/adapter/card supply requirements, logic compatibility and power
  budget. Verify the real rails, footprint and continuity before connecting
  devices. Finish the optional activity LED circuit rather than inferring it
  from the draft BOM.
- Verify documented CF True IDE/slave selection, both device identities, stock
  GD-ROM boot and GD-ROM operation after cold starts and resets.
- Use a sacrificial CF card for sustained hash-verified reads/writes, reset and
  power-cycle checks, then the large exFAT card. Accept DMA separately only
  after verified transfers and game/ripper tests.

## DIY stock/custom BIOS board

A validated custom schematic and exact flash-chip choice have not been
recovered. Published jskyboo VA1 triple-BIOS boards are useful reference
architectures, not a verified dual-BIOS design for this console. Their public
pages list components and board downloads but no explicit design license.

Before committing our own layout: identify the installed ROM and chosen flash
package; verify address/data/control mapping, supply, read timing and bus mode;
ensure exclusive output selection with a defined stock default; and establish
write protection, programmer compatibility and verified readback/recovery.
Check PCB thickness and clearance against the actual console. Preserve stock
boot as the first acceptance milestone, then prove custom boot and repeated
cold starts. Do not call the board fabrication-ready until these checks and
schematic/layout review are complete.
